Graduation Project Backend Presentation Guide

1. Project summary
This project is the backend of my graduation app. I use Laravel to receive requests from the mobile app, process the data, and return JSON responses. The source of truth for the database is schema.sql.

2. My main idea
I built the backend so the app can handle authentication, property management, booking, payment, messages, and reviews in a clean and secure way. The backend is role-based, so each user only works with the data they own.

3. Why I use Laravel
I use Laravel because it gives me routing, validation, Eloquent models, authentication, and API responses in one organized framework. That helps me build the project faster and keep the code easier to explain during the defense.

4. Why I use XAMPP
I use XAMPP because it gives me PHP and MySQL locally on Windows. That lets me test the backend on my own machine before deployment. In this project, XAMPP is for local development only.

5. Why I use Composer and GitHub
I use Composer to install Laravel and its packages. I use GitHub to store the code, share it with the team, and track changes safely.

6. What schema.sql means
schema.sql is the source database design. It defines the real tables that the backend must follow. In this project, the important tables are users, properties, property_images, bookings, payments, messages, reviews, notifications, and personal_access_tokens.

7. Main roles
The user roles are admin, owner, and user. The owner creates and manages properties. The user makes bookings, payments, messages, and reviews. The admin role is reserved for management tasks and can be created manually or through seeding.

8. Main relationships
One user can own many properties. One property can have many images, many bookings, and many reviews. One user can create many bookings, messages, and reviews. One booking has one payment.

9. Backend workflow step by step
First, the user registers or logs in. Then the app receives a Sanctum token. After that, the user can read properties, open a property detail page, create a booking, make a payment, send messages, and add reviews. Every protected action checks the token and the user role.

10. Authentication layer
I use Sanctum for token-based authentication. The API has register, login, me, and logout endpoints. Register creates a new account, login returns a token, me returns the current authenticated user, and logout revokes the token.

11. Property layer
The schema uses the properties table as the main accommodation table. In the code, some older file names still say Listing for continuity, but the actual data now belongs to the properties table. A property stores owner_id, title, price, location, description, rooms, amenities, and status.

12. Property images
The property_images table stores multiple images for one property. Each image has a path and sort_order. This keeps the database normalized, because one property can have more than one image without repeating the property data.

13. Booking layer
The bookings table stores user_id, property_id, date_from, date_to, guests, total_price, status, and notes. I also added overlap checking so the same property cannot be booked for conflicting dates.

14. Payment layer
The payments table stores one payment for one booking. It includes amount, method, status, reference, paid_at, and notes. I made the booking_id unique so one booking cannot have duplicate payments.

15. Messages and reviews
The messages table supports chat between users. The reviews table stores rating and comment for a property. These tables are part of the source schema, so the backend is prepared for chat and feedback features as part of the same system.

16. Validation and security
I validate every request before saving it. I also check ownership so the owner can manage only their properties, and the user can manage only their own bookings, payments, messages, and reviews. This prevents unauthorized access.

17. Database and runtime settings
I changed the environment to match the schema-driven design. Session, cache, and queue are kept simple with file and sync drivers, so the database stays focused on the business tables from schema.sql.

18. What I changed in the backend
I updated the migrations, models, controllers, routes, factory, and seeder so they follow the source schema. I also added API endpoints for properties, bookings, payments, reviews, messages, and property images.

19. What I can say in the defense
If an instructor asks me what I did, I can say: I took the provided schema as the source of truth, aligned the Laravel backend with it, and protected the data with authentication, validation, and role-based access control.

21. Short closing summary

7. How the User model works
This file is the model for the users table and also handles authentication support.

- namespace App\Models: keeps the class inside Laravel's models area.
- use lines: import UserFactory, HasFactory, Authenticatable, HasMany, and Notifiable so the class can use them.
- class User extends Authenticatable: makes the model work with Laravel's login and authentication system.
- HasFactory: allows fake user records for testing and seeders.
- fillable: lists the user columns that can be saved in bulk, such as name, email, phone, role, status, and password.
- hidden: hides password and remember_token when the model is converted to JSON.
- casts(): converts email_verified_at into a datetime and password into a hashed value.
- listings(): defines that one user can have many listings.
- hasMany(Listing::class, 'owner_id'): links the user to the listings table through the owner_id column.
- HasMany: the relationship type returned by listings().
- Listing::class: points to the Listing model class in the same App\Models namespace.

8. How the Listing model works
This file is the PHP model for the listings table. It does not create the table by itself; the migration does that. The model tells Laravel how to use the table.

- namespace App\Models: keeps the class inside the models folder in Laravel.
- use lines: import HasFactory, Model, and BelongsTo so the file can use them.
- HasFactory: lets Laravel generate fake listing data for testing and seeders.
- class Listing extends Model: makes this file an Eloquent model connected to the database.
- fillable: lists the columns that are allowed to be saved in bulk.
- casts(): converts values into useful PHP types like decimal, boolean, and date.
- owner(): defines that one listing belongs to one user through owner_id.
- BelongsTo: the relationship type returned by owner().
- User::class: points to the User model class.

9. How the migration works
This file is the blueprint for the listings table. It does not write raw SQL directly. Laravel reads this PHP migration and converts it into SQL for MySQL.

- return new class extends Migration: creates an anonymous migration class.
- up(): the method Laravel runs when applying the migration.
- Schema::create('listings', ...): tells Laravel to create the listings table.
- Blueprint $table: the object used to define columns and constraints.
- down(): the method Laravel runs when rolling back the migration.
- Schema::dropIfExists('listings'): removes the listings table only if it exists.
- This is not error handling. It is the reverse step for undoing the migration.

10. How the Listing API works
This is the next backend layer after the model and migration. The controller receives requests and returns listing data as JSON, and the API route file defines the endpoints.

- backend/app/Http/Controllers/ListingController.php: handles requests for listings and returns JSON.
- JsonResponse: the return type tells Laravel that these methods send JSON back to the frontend.
- index(): starts with Listing::with('owner') so the owner data is loaded with each listing before the query runs.
- filled(), has(), query(), and boolean() are Laravel request helper methods, while trim() is a normal PHP function.
- $request->filled('search'): checks whether the search field exists and is not empty.
- trim((string) $request->query('search')): removes extra spaces from the search text and makes sure it is treated as a string.
- $query->where(function (Builder $listingQuery) use ($search): void { ... }): groups the search conditions so one keyword can match several columns.
- where and orWhere with like: search the title, description, city, area, and address for similar text.
- The filter if blocks add city, listing_type, status, gender_preference, furnished, is_featured, min_price, max_price, bedrooms, bathrooms, and available_from only when the user sends them.
- match ($request->query('sort', 'latest')): chooses the sorting mode. latest() and oldest() are Laravel query methods, and orderBy() / orderByDesc() are used for custom sorting.
- return response()->json($query->get()): executes the query and returns the final list as JSON.
- show(Listing $listing): uses route model binding so Laravel injects the requested listing record, then load('owner') loads that listing's related user.
- store(Request $request): validates the incoming data, creates a new listing record, and returns it as JSON.
- update(Request $request, Listing $listing): validates the data again, updates the existing listing, and returns the updated listing.
- destroy(Listing $listing): deletes the listing and returns a success message.
- owner here is not the latest owner. It is the user connected to that listing through owner_id.
- backend/routes/api.php: defines the GET, POST, PUT, and DELETE routes for the listings API.
- backend/bootstrap/app.php: tells Laravel to load the api.php route file.

11. How the Booking model works
This file is the model for the bookings table. It connects a tenant, a listing, and the linked payment record to a reservation record.

- namespace App\Models: keeps the class inside Laravel's models area.
- use lines: import HasFactory, Model, and BelongsTo so the file can use them.
- class Booking extends Model: makes this file an Eloquent model connected to the database.
- fillable: lists the booking columns that can be saved in bulk.
- casts(): converts check_in_date and check_out_date into dates, guests into an integer, and total_price into a decimal.
- tenant(): says one booking belongs to one user who made the booking.
- listing(): says one booking belongs to one listing.
- payment(): says one booking has one payment record.

12. How the Booking migration works
This file is the blueprint for the bookings table. Laravel converts it into SQL for MySQL just like the listings migration.

- up(): creates the bookings table.
- tenant_id: connects the booking to the user who made it.
- listing_id: connects the booking to the selected listing.
- check_in_date and check_out_date: store the stay dates.
- guests: stores how many guests are included.
- total_price: stores the booking cost.
- status: tracks the booking state.
- down(): removes the bookings table if the migration is rolled back.

13. How the Booking API works
This is the next backend layer after the booking model and migration. The controller receives requests and returns booking data as JSON, including the payment relation, and the API route file defines the endpoints.

- backend/app/Http/Controllers/BookingController.php: handles requests for bookings and returns JSON.
- index(): returns all bookings with the tenant, listing owner, and payment loaded.
- show(Booking $booking): returns one booking with its related tenant, listing owner, and payment.
- store(Request $request): validates the booking data, creates a new booking record, and returns it as JSON.
- update(Request $request, Booking $booking): validates the data again, updates the booking, and returns it.
- store() and update() also check whether the listing is already booked for the selected dates before saving.
- If the dates overlap with an existing booking, Laravel returns a validation error and stops the save.
- destroy(Booking $booking): deletes the booking and returns a success message.
- backend/routes/api.php: defines the GET, POST, PUT, and DELETE routes for the bookings API.
- backend/tests/Feature/BookingAvailabilityTest.php: proves that the booking controller rejects overlapping dates on create and update. It uses RefreshDatabase for a clean database in each test, creates owner and tenant fixtures, and expects a 422 validation error on listing_id when the dates conflict.

17. How the Auth API works
This layer handles registration, login, profile lookup, and logout for the mobile app. It uses Sanctum so the frontend can send a bearer token with each protected request.

- backend/app/Http/Controllers/AuthController.php: handles register, login, me, and logout requests and returns JSON.
- register(Request $request): validates the new user, creates the account, and returns a token.
- login(Request $request): checks the email and password, then returns a fresh token if the credentials are correct.
- me(Request $request): returns the currently authenticated user.
- logout(Request $request): deletes the user's personal access tokens and clears the cached guards so the token cannot be used again.
- backend/routes/api.php: adds the public auth routes and protects the authenticated routes with auth:sanctum.
- backend/database/migrations/2026_04_16_000000_create_personal_access_tokens_table.php: creates the table that stores Sanctum tokens.
- backend/tests/Feature/AuthApiTest.php: proves that registration, login, protected access, and logout token revocation all work.
