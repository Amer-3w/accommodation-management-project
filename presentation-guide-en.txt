Graduation Project Backend Presentation Guide

1. Project summary
This project is the backend of my graduation app. I built it with Laravel so it can receive requests from the Flutter app, process the data, and return JSON responses. The database source of truth is schema.sql.

2. Stack
I used Laravel, PHP, XAMPP, MySQL, Composer, Sanctum, and GitHub. XAMPP gives me the local PHP and MySQL environment on Windows, and GitHub keeps the code synchronized for the team.

3. Source of truth
I treat schema.sql as the real database design. It defines the tables the backend must follow, including users, properties, property_images, bookings, payments, messages, reviews, favorites, support_messages, user_whatsapp_numbers, and personal_access_tokens.

4. Roles
The main roles are admin, owner, and user. The owner manages properties. The user makes bookings, payments, favorites, messages, and reviews. The admin handles management tasks.

5. Workflow
First the user registers or logs in. Then Sanctum returns a bearer token. After that, the app can read properties, view details, create bookings, pay, send messages, save favorites, submit reviews, manage WhatsApp numbers, and contact support.

6. Authentication
The API has register, login, me, update profile, and logout endpoints. Register creates the account, login returns a token, me returns the authenticated user, update profile edits the current account, and logout revokes the token.

7. Property layer
The main accommodation table is properties. In the code, the model name is still Listing for continuity, but it points to the properties table. A property stores owner data, title, price, location, description, rooms, bathrooms, discounts, contact fields, status, and availability.

8. Property images
The property_images table stores multiple images for one property. This keeps the database normalized because one property can have many images without repeating the property record.

9. Booking layer
The bookings table stores user_id, property_id, date_from, date_to, guests, notes, base_price, price_period, number_of_days, base_total, discount_percent, discount_amount, service_fee, security_deposit, final_total, and status. I also added overlap checking so the same property cannot be booked for conflicting dates.

10. Booking pricing
The backend now calculates the booking breakdown from the property data when the frontend does not send every value. That keeps the price fields consistent and matches the schema-driven design.

11. Payment layer
The payments table stores one payment for one booking. It includes amount, payment method, status, transaction reference, paid_at, and notes. I kept booking_id unique so one booking cannot have duplicate payments.

12. Messages
The messages table supports chat between users. I added message status, attachment_path, and read_at handling so messages can move through sent, delivered, and seen states.

13. Reviews
The reviews table stores rating and comment for each property. I also added owner reply, reply timestamp, and moderation timestamp so the owner and admin can manage feedback.

14. Favorites and WhatsApp numbers
I added favorites so a user can save properties, and user_whatsapp_numbers so a user can store more than one WhatsApp contact number. Both are now exposed through the API.

15. Support messages
I added support_messages for the contact form or help requests. A guest or authenticated user can send a support message, and the admin can review or update it.

16. Security
I validate requests before saving them, and I check ownership so each user can manage only their own data. That protects properties, bookings, payments, messages, reviews, favorites, and profile data.

17. What I changed
I updated the migrations, models, controllers, routes, factory, and seeder so they follow schema.sql. I also added the new API endpoints needed for the Flutter app.

18. Testing
I ran the Laravel test suite with XAMPP PHP, and all tests passed: 12 tests and 39 assertions. That confirms authentication, booking overlap checks, role access, and payment ownership still work after the schema update.

19. What I can say in the defense
If I am asked what I did, I can say: I took schema.sql as the source of truth, aligned the Laravel backend with it, added role-based protection and validation, and prepared the API for the Flutter interface.

20. Short Q&A
What is the source of the database?
I use schema.sql as the source of truth.

Why did I use Laravel?
Because it gives me routing, validation, Eloquent, Sanctum authentication, and clean API responses.

How do I protect data?
I use Sanctum plus role and ownership checks.

How do I prevent double booking?
I check overlapping booking dates before saving.

What remains after the backend?
The next step is connecting the Flutter app to these protected endpoints.
